# 构建与发布

## 每次上传都构建 APK

推送前，在项目根目录运行 `powershell -ExecutionPolicy Bypass -File tools/package.ps1`。脚本构建 APK、执行 Lint、校验签名，将版本化 APK 和 SHA-256 文件写到 `releases/`；失败时应先修复，不继续发布。

GitHub Actions 对每次 push 自动构建并保存带提交标识的 APK Artifact，保存 90 天。Pull Request 和手动运行也执行相同检查。构建成功后可从 Actions 运行页面下载；失败时不会生成 Release。

## 发布版本

1. 在 `app/build.gradle` 同时递增 `versionCode` 和 `versionName`。
2. 本地构建并测试，将源码提交并推送。
3. 创建与版本一致的标签，例如 `git tag v0.3.0`，再执行 `git push origin v0.3.0`。
4. 标签触发工作流，完成构建后自动创建 GitHub Release，附加 APK 和 `SHA256SUMS.txt`。

Release 资产独立保存，不将 APK 或签名密钥提交到源码仓库。重新运行同一标签工作流会更新该标签的资产。

## 签名与覆盖安装

当前为调试签名：本地使用开发机的 Android 调试密钥，CI 使用运行环境生成的调试密钥。不同环境或不同 CI 运行的签名可能不同，因此不能保证相互覆盖安装。不要为此直接卸载已有应用，卸载会删除本机数据；可以继续使用同一开发环境生成的安装包。

要长期发布可连续覆盖升级的版本，应单独配置稳定的发布签名：密钥保存在私有密钥存储，CI 通过 GitHub Actions Secrets 注入，密码通过环境变量读取；私钥及密码绝不能提交到公开仓库。当前仓库没有预置发布密钥，也不应将调试签名作为正式分发签名。

应用显示名称为“轻启”，项目名为 `LightStart`；为保留此前安装的数据，安装标识与内部存储名称保持兼容。
